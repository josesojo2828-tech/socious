## Context & Motivation

Hoy un paciente cuenta con su contraseña puesta por el profesional, o con una contraseña temporal compartida por todos (`Nutringest2026!`). Ambas cosas sonOSA: una credencial conocida por el público sobre cuentas reales (ver `security-hardening-followups.md` S1). Y el paciente pediátrico no tiene un camino propio: no hay figura de representante, así que no hay a quién notificar.

Este feature reemplaza la contraseña temporal por una **invitación de un solo uso** que permite al paciente (o al representante de un menor) **definir su propia contraseña**, y agrega el alta del **paciente pediátrico con representante**.

## Specs

> Los fragments del usuario son verbatim.

### S1: Invitación por correo para crear la contraseña
> "vamos a montar una lógica segura para notificar al paciente via correo electrónico, y que le llegue el correo para crear la password"

- El profesional (o el sistema) genera una **invitación** para un paciente: el paciente recibe un correo con un enlace seguro y **define su propia contraseña**.
- El token es **aleatorio, de un solo uso, con expiración** y se guarda **hasheado** (sha256) — un dump de la base no sirve para completar la invitación.
- La invitación genera la cuenta del paciente con el permiso PATIENT y **no** una contraseña temporal.
- Reenviar una invitación no puede revelar si el paciente existe (misma respuesta siempre).
- El correo **no** debe fallar la creación del paciente: si el SMTP no está configurado, la operación clínica se completa y la invitación queda pendiente de envío.

### S2: Paciente pediátrico con representante
> "vamos a hacer una tab o algo para la creacion del paciente pediatrico, con el correo del representante y ahi mismo se agreguen los datos del representante y se guarden en base de datos"

- El alta de paciente tiene una **pestaña "Pediátrico"** que activa el registro como menor y captura los datos del **representante**: nombre, parentesco, correo, teléfono y documento opcional.
- Los datos del representante se **guardan en base de datos** (no en un campo suelto del paciente).
- Para un menor, la **cuenta y las notificaciones van al representante**, no al menor. El portal del representante muestra los datos del menor a su cargo.
- La invitación por correo de S1 se envía al **correo del representante** cuando el paciente es pediátrico.

### S3: Compatibilidad con lo que ya existe
- El flujo de `forgot-password` / `reset-password` y el de `verify-email` se **mantienen** (los usa el resto de los usuarios). La invitación es un camino nuevo, no una modificación de los viejos.
- El alta de paciente actual (formulario web, app móvil, API) no se rompe: la pestaña pediátrica es **opcional** y solo aparece cuando aplica.

## Design decisions

| Decisión | Elección | Motivo |
| --- | --- | --- |
| Almacén de la invitación | Modelo `PatientInvitation` (token hasheado, `expiresAt`, `acceptedAt`, `revokedAt`, `createdById`) | Rastro de auditoría y semántica propia: la invitación NO es un reset de contraseña |
| Token | `crypto.randomBytes(32)` en base64url, guardado como sha256 | Un solo uso + largo + no reutilizable desde un dump |
| Expiración | 72 horas | Supuesto documentado (el spec no fija plazo) |
| Cuenta del menor | `Patient.userId` apunta al `User` del representante | El portal del representante muestra al menor; no hace falta un modelo de relación nuevo |
| Representante | **Reutilizar `PediatricHistory`** (campos `representativeName/Phone/Email/Relationship` que YA existen) + `Patient.isPediatric` | **Corrección 2026-10-21**: el modelo `PatientRepresentative` que se había previsto YA NO se crea. Los datos del representante existen como campos planos en `PediatricHistory`, con service, repository, DTO y API completos (`POST /api/pediatric-history/create/api`). Un modelo nuevo sería duplicar la misma información con otra forma |
| Detección de menor | Campo explícito `Patient.isPediatric` | Derivarlo de la edad hace que un paciente que envejece cambie de flujo |
